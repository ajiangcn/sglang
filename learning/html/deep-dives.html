#A worked two-request story

Think of a finished request leaving its working notes on a shelf. The next request can borrow those notes without keeping the first request alive. But before starting work, it must protect the notes from being reclaimed.

Start with an empty cache. A's prompt is P0..P19. After A finishes, B arrives with P0..P11, U12..U19, where U12 != P12. These names stand for token IDs, not words. Both requests use greedy generation and produce exactly two output tokens, named A0, A1 and B0, B1; assume no earlier stop. Use ordinary dense, full-attention text generation: no prompt logprobs, media, LoRA, speculation, hybrid state, sessions, or host offload. The requests share the same cache namespace, insertion is enabled, and nothing is evicted between them.

Selected source path, not a universal default: at local revision 5eda6b7e674458c0c01f93801012b6ff6c15064e, default_radix_cache_factory / create_unified_radix_cache lead this built-in dense case to a FULL-only UnifiedRadixCache. We deliberately read its Python UnifiedTreeCore, selected by the lab fixture's _TREE_CORE_TEST_BACKEND. An actual engine resolves its core through select_tree_core_backend; do not assume every installation executes the Python walk.

Page size 4 is illustrative geometry, not a GPU launch recommendation. Assume sufficient capacity and an input/chunk budget allowing B's eight new prompt positions in one step. A's prefill row below totals any chunks it needed. Count useful completed model work, not padded rows or overlapped lookahead.

Point in the serial storyNewly computed prompt positionsUseful KV positions for this requestCache state
A completes prefill and chooses A02020Its computed prompt can be checkpointed and protected
A feeds A0, chooses A1, then finishes021 before release20 page-aligned prompt positions remain reusable, with no live request holding them
B matches and is admitted012 matched, no new forward yetB reacquires protection of P0..P11; A is already finished
B prefills U12..U19 and chooses B0812 + 8 = 20Three shared pages plus two new suffix pages on B's path
B feeds B0, chooses B1, then finishes021 before releaseWith no eviction, the tree retains 12 + 8 + 8 = 28 distinct prompt positions, all unheld

Read the arrows as changes of responsibility, not GPU kernels or a timing chart. A hit answers what is reusable; admission answers what can safely run; forward metadata answers which positions and locations this execution uses. Here is the source proof for the table and those boundaries.

#Match: a valid prefix is not permission to allocate

Req.init_next_round_input / _compute_max_prefix_len cap this lookup at input_len - 1 = 19. match_kv_cache adopts the result into req.prefix_len and the node handles. Through UnifiedRadixCache.match_prefix, UnifiedTreeCore.match_prefix / _match_prefix_helper page-align the key to 16 positions, then find only 12 equal positions before the divergent page. RadixKey.match_at / child_key_at define the token/page and namespace comparisons; FullComponent.create_match_validator requires device state for this device-only hit.

If A left a compressed 20-token segment, this lookup can split the tree at 12 without allocating another copy of the prefix KV. UnifiedTreeCore._split_node and FullComponent.redistribute_on_node_split split keys and clone location-index slices, not the model's K/V tensors. Three shared pages need not mean three tree nodes.

#Admit: do not spend the memory you are about to borrow

Scheduler._get_new_batch_prefill_raw checks request capacity, refreshes the match, and invokes PrefillAdder.add_one_req. Inspect its _lock_node, _select_prefill_admission, and _commit_prefill_admission: the temporary pin removes the selected prefix from evictable capacity before the budget decision, then a successful admission installs req.lock and sets req.extend_end = 20. This prevents counting B's required prefix as memory available to replace.

This is where to check our capacity and eight-token-chunk assumptions, together with PrefillAdder._check_prefill_budget, ceil_paged_tokens, and _update_prefill_budget in that same file. For a fixed token pool, PrefillBudget._available_and_evictable / check_prefill / reserve show how reclaimable capacity and reservations enter the decision. New input work, future-output headroom, page overhead, and request slots are different constraints. Eight uncached tokens do not by themselves guarantee admission.

UnifiedRadixCache.lock / unlock carry a TreeLock receipt; the Python core delegates FULL protection to FullComponent.acquire_component_lock / release_component_lock. At the stable boundaries, the shared prefix has zero request holders after A, one for admitted B, then zero after B. The temporary admission pin is not a second live request.

#Prepare and forward: eight inputs still need a twenty-position context

ScheduleBatch.prepare_for_extend slices off the matched prefix. For B, prefix_lens=[12], extend_lens=[8], seq_lens=[20], and extend_num_tokens=8. alloc_for_extend / write_cache_indices put the existing prefix locations and newly allocated suffix locations into B's request-to-token row. Reuse means sharing those earlier physical locations, not copying twelve prompt IDs into the model input again.

Preparation leaves input_ids=None and stages the eight IDs in prefill_input_ids_cpu. Scheduler.run_batch calls resolve_forward_inputs to materialize them at forward entry. This separates CPU planning from the device-copy boundary; on ordinary decode, that same resolver instead gathers the previous step's sampled token.

TpModelWorker.forward_batch_generation passes the ScheduleBatch directly to ForwardBatch.init_new: there is no ModelWorkerBatch hop in this revision. Inspect compute_position and compute_position_torch there to derive positions 12..19. The boundary builds per-forward metadata, including the KV-location plan, from the scheduler's plan; it is not a deep copy of all state. An eight-element input slice paired with positions 0..7 would describe the wrong computation even if allocation succeeded.

#Finish: releasing a request is not erasing its useful work

SchedulerBatchResultProcessor.process_batch_result_prefill appends the first chosen output and calls checkpoint_kv_cache for an unfinished ordinary request. Choosing A0 does not compute its KV. ScheduleBatch.prepare_for_decode prepares the later one-token step that consumes it. process_batch_result_decode and _handle_finish_state_updated_req in the result processor append the second output, update finish state, and reach release_kv_cache.

release_kv_cache uses Req.owned_kv_len, refreshes the token IDs, and checkpoints before freeing the unprotected tail and the request row. UnifiedRadixCache.checkpoint_into_tree retains page-aligned KV and moves the lock to the canonical tree path. In this ledger, 21 computed positions floor to 20 at page size 4, so the one computed output position is not retained in the tree; the last chosen output has not been fed through the model at all. Releasing the lock makes the retained prompt evictable, not already freed. UnifiedRadixCache.evict is a separate reclamation operation.

Thus the prompt-work arithmetic is A:20, B:8, not 20 + 20. The subsequent single-token decode step for each request is separate. This is neither a latency prediction nor a throughput measurement.

Surprising edge case: what if B's entire 20-token prompt were identical?

Even with all 20 positions cached, this request path caps matching at 19 before page alignment. With the illustrative page size 4, that allows a 16-token hit and four recomputed prompt positions, not zero. The final prompt position must still produce the logits used to choose the next token, even without requested prompt logprobs. Check Req._compute_max_prefix_len, UnifiedTreeCore.match_prefix, and TpModelWorker.forward_batch_generation. Our divergent B already stops matching at 12, so that cap does not change its eight new positions.

#1. Radix reuse: keys, values, and ownership

Sources: classic radix cache, prefix-cache interface, request state.

This classic RadixCache is a compact alternative to study, not an additional stage before the worked story's unified controller. Verify selection in default_radix_cache_factory before applying its method names to a serving trace.

A radix tree stores compressed token-prefix segments. A path identifies a prefix; its cached values identify the corresponding KV locations. The tree does not contain an attention matrix and does not replace the attention kernel.

In the inspected classic implementation:

  • match_prefix aligns the key to cache-page granularity and returns a MatchResult describing the valid matched prefix and nodes.
  • Matching can split a segment to expose a shared boundary without duplicating the underlying semantic prefix.
  • insert adds eligible token segments and associated locations.
  • inc_lock_ref protects the matched path; dec_lock_ref makes appropriate segments evictable again.
  • evict chooses eligible leaves under the configured eviction strategy, frees their segments, and can expose newly eligible parent leaves.

Do not assume every eviction policy is LRU; inspect configuration.

#Worked branching example

For readability, treat letters as token IDs and use page size one:

example / trace
A: [a b c d e]
B: [a b c x y]

After branching:
root -> [a b c] -> [d e]
               -> [x y]

Request B can reuse the state for [a b c], then compute [x y]. If A and B are both active, the shared prefix must remain protected. Finishing A must not make B's shared state reclaimable. If page size is four instead, a three-token shared prefix may provide no complete reusable page in this simplified example.

The inspected key logic also carries namespace/cache-salt information. Adapter or media identity must be represented consistently by the upstream path; the mere existence of an extra_key field does not prove a caller supplies all needed identity.

#Important distinctions

Trace all four when debugging stale KV. A correct tree lookup cannot repair a wrong request-row mapping or premature allocator reuse.

#2. Unified cache: one logical tree, several physical state types

Sources: controller, tree core, component design.

The unified design separates logical tree decisions from physical resource actions. Full-attention, SWA, and Mamba components maintain their own state, locks, residency, and eviction behavior.

A node can retain logical structure even when one component's data has been evicted. Therefore, finding a token path is not sufficient for a valid hit: every required component must permit resumption at that boundary.

ComponentRetained stateWhy prefix validation differs
FullKV across accessible historyMissing old KV can invalidate the prefix
SWAWindow-relevant KVOld positions outside the needed window can be absent
Mamba/SSMRecurrent state/checkpointsBranching may require a copy or specific checkpoint

The tree emits deferred actions and the cache/controller performs pool/host operations. This keeps the logical index from directly owning every physical copy/free behavior.

The component documentation specifies per-component lock references and coordinated eviction priorities. Do not transfer the classic tree's one-payload reasoning unchanged to this design.

Invariant

a reported reusable prefix has a compatible resume state in every required pool, and a branch cannot mutate another request's recurrent state. Copy-on-write may apply to state components even when attention KV is shareable as immutable prefix data.

Read tests for unified allocation/eviction and unified lock references. Determine which cache implementation your model/configuration selects before choosing a regression test.

#3. HiCache: a hit is useful only if state arrives in time

Read HiCache design, host pools, and storage backends.

The documented tier scope is:

example / trace
L1 = instance-local GPU memory
L2 = instance-private host memory
L3 = configured storage backend, potentially shared

Two instances on the same node do not automatically share L2. A file-backed L3 is not cluster-wide unless its storage configuration makes it so.

Workflow:

  1. Match device/host-resident prefixes.
  2. Query/prefetch eligible missing state from storage.
  3. Move required state into device-accessible locations.
  4. Coordinate readiness with scheduling/execution.
  5. Back up or write back newly produced state under the selected policy.
  6. Evict only resources whose ownership and in-flight transfers permit it.

Two costs compete:

example / trace
restore cost = lookup + storage/network + host/device copy + synchronization
recompute cost = prefill work that would otherwise be repeated

A larger hit count can make latency worse if restoring small/cold objects is slower than recomputing them. Report bytes, useful reused tokens, transfer overlap, and p95/p99 TTFT, not only a hit ratio.

HiCache stores model state; it is not the same as an image processor or encoder embedding cache.

#4. Scheduling: policy plus capacity

Read scheduler, scheduling policy, and allocation.

get_next_batch_to_run handles pending cleanup/cache events, merges eligible prefill results into running work, and chooses the next plan. run_batch dispatches according to the batch's forward mode and enabled execution path.

Separate the questions:

  • Ordering: which waiting request should be considered next?
  • Admission: can it fit the needed request slots, token/state capacity, chunks, and reservations?
  • Execution shape: how many new positions and which forward mode?
  • Retention: what remains cached/protected afterward?

A prefix-aware policy can improve reuse while worsening fairness for unrelated requests. A token budget can leave memory unavailable for the next decode. Chunking can improve decode latency but add prefill overhead. These are workload tradeoffs, not contradictions.

#Ordering policies in the inspected checkout

--schedule-policy in schedule arguments defaults to fcfs. Schedule policy divides policies into two families:

FamilyPoliciesBehavior to verify
Cache-aware (CacheAwarePolicy)lpm longest prefix match, dfs-weight, hrrnUse radix-tree matches to order waiting requests
Cache-agnostic (CacheAgnosticPolicy)fcfs, lof longest output first, random, routing-keyIgnore prefix structure
Other choicespriority, shortest-prefill-firstInspect validation and selection code before use

_determine_active_policy silently downgrades lpm and hrrn to fcfs when the waiting queue exceeds WAITING_QUEUE_PREFIX_MATCH_MAX (128), because matching every queued request becomes too expensive. An LPM benchmark with a deep queue may actually be measuring FCFS.

#Admission reserves future decode memory

A useful distinction is admission headroom versus allocated KV. PrefillAdder.add_one_req checks a candidate's uncached input plus its capped remaining output allowance and page overhead. The running-request estimate is a separate calculation in _get_running_request_total_token_offset:

example / trace
estimated_running_headroom(req) =
    min(max_new_tokens - generated_so_far, CLIP_MAX_NEW_TOKENS)
    * new_token_ratio          (ratio is 1.0 when ignore_eos is set)

Do not multiply a fresh candidate's allowance by new_token_ratio merely because the running-request estimate does. Inspect _update_prefill_budget and the allocator's create_prefill_budget implementation for the selected pool; the fixed-token PrefillBudget.reserve adds the candidate's output allowance without that ratio. These are scheduling reservations, not proof that every future output already has a KV position.

NewTokenRatioTracker controls the ratio:

  • It starts at SGLANG_INIT_NEW_TOKEN_RATIO * schedule_conservativeness, capped at 1.0.
  • Each quiet decode step decays it linearly toward a floor, admitting more work as confidence grows that requests stop before max_new_tokens.
  • After a retraction it is re-estimated from observed progress: (decoded + RETRACT_DECODE_STEPS * num_reqs) / total_max_new_tokens.

--schedule-conservativeness therefore trades admission aggressiveness for retraction risk. Clients that send huge max_tokens values they never use make this estimator pessimistic and reduce concurrency.

#Retraction when the estimate is wrong

ScheduleBatch.check_decode_mem asks the allocator whether the next decode step fits. If not, retract_decode in schedule batch:

  1. Orders requests by --retraction-policy. The default length policy keeps requests with more generated output and retracts those with the least output first, breaking ties by retracting longer inputs first. The priority policy uses request priority.
  2. Pops victims until the remaining batch fits, always keeping at least one.
  3. Releases each victim's memory without inserting it into the radix tree, because the space is needed immediately.
  4. Aborts, rather than requeues, beam groups and requests that cannot resume, for example because no KV backup exists in the configured mode.
  5. Aborts the last request if even it cannot fit, instead of crashing.

Compare vLLM preemption:

QuestionvLLM V1 (inspected)SGLang (inspected)
When is future decode memory accounted?On demand, step by stepEstimated and reserved at admission
What happens on shortage?Preempt a running request and recompute laterRetract decode requests and adjust admission ratio
Default victimMost recently admitted running requestLeast generated output, then longer input
Cache after evictionFreed blocks keep hashes until reassignedRetracted KV is not inserted into the radix tree
Tuning knobBatch/token limits, memory utilizationschedule_conservativeness, retraction policy, limits

Neither design is universally better. Reservation reduces wasted recompute but can leave capacity idle when outputs are shorter than predicted. On-demand allocation packs more aggressively but can thrash under long outputs. Measure admitted concurrency, retractions or preemptions, and recomputed tokens on your own output-length distribution.

Track waiting/running counts, actual prefill chunk sizes, newly computed versus reused tokens, retractions, and iteration duration. A peak-throughput number does not identify the scheduling mechanism that improved it.

#5. Forward execution, metadata, and overlap

Sources: TP worker, ForwardBatch, runner.

forward_batch_generation converts scheduler-owned data into forward metadata, calls the runner, and forms generation results. Verification modes can skip ordinary sampling; overlap/grammar paths can defer it.

For one request, explicitly record:

example / trace
request row / request ID
input token slice
position slice
prefix and total sequence lengths
cache write locations
attention read mapping
sampling and grammar state

Flattening several ragged requests into tensors is efficient only if these boundaries agree. A wrong offset can produce plausible but unrelated text.

#What RadixAttention does

The layer adapts Q/K/V and forward metadata into the configured attention execution path. Piecewise compilation and specialized wrappers can alter dispatch.

Its job is not to walk prefix strings. Follow the selected attention backend into its metadata setup, cache access, and kernel call. Keep model semantics, metadata, and device layout separate in your explanation.

#Graphs and streams

Graph/compile setup is reached through the runner's initialization methods and execution helpers. Read compilation for the actual selected path, not an old tutorial's graph-runner filename.

The overlap scheduler coordinates schedule and forward streams, result queues, and shared-read fences. A tensor's Python lifetime and the completion of a GPU read are different facts. Reusing pinned CPU buffers while an async copy is outstanding is also unsafe.

Proof of useful overlap requires a timeline showing less exposed idle time; adding streams does not itself demonstrate parallel execution.

#6. Multimodal source trace: Qwen2.5-VL

Read model, processors, and embedding integration.

The model exposes pad_input_ids to establish multimodal token structure. Its forward uses multimodal rotary positions when configured and delegates embedding integration to general_mm_embed_routine.

Follow general_mm_embed_routine in the embedding integration helpers. Inspect how encoder outputs, cached embeddings, and precomputed inputs affect the selected path instead of assuming every request always runs the encoder inline.

Key checks:

  1. Do media-item order and placeholder spans agree?
  2. Do feature count and padded token count agree after processor transforms?
  3. Are image/video positions correct, including temporal dimensions?
  4. Does a chunk boundary preserve required media/state semantics?
  5. Are cached features and LM KV keyed by the right identity?

The EPD guide distinguishes encoder output transport from global embedding caching. Enabling a transport does not imply cross-instance embedding reuse.

A speculative proposal count is not an accepted-token count. A transfer being submitted is not it being complete. A node existing is not its data being resident. These distinctions are central to both correctness and performance.

#8. Debugging order

  1. Reproduce using exact model/tokenizer/template, request tokens/media, sampling settings, effective configuration, and topology.
  2. Classify the first divergent boundary: preprocessing, prefix match, allocation, metadata, forward, sampling, output, or cleanup.
  3. Minimize: one GPU, eager/baseline execution, no speculation, simple cache mode where supported. Change one axis at a time.
  4. Compare inputs and logits/state, not only final free-form text.
  5. For a hang, collect all-rank progress/stacks and identify the first unequal control-flow or collective sequence.
  6. After correction, re-enable the original features and replay the original workload. Passing a simpler path alone does not close the bug.

Use profiling guidance and the source labs to turn this into repeatable practice.
