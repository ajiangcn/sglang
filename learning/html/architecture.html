SGLang architecture: from request to token

Index and revision | Deep dives | Source labs

#Start here: what happens after you press Send?

SGLang has to do more than call a neural network. It must remember who asked, decide whose work runs next, keep useful model state, and deliver an answer without mixing requests.

The simplest mental model: receive a request, run a model step, save its progress, and repeat until the request is finished.

On your first read, ignore distributed execution, speculative decoding, and specialized caches. Follow one request on one GPU. The full source reference is folded below for your second pass.

#Watch two tokens being generated

Suppose the prompt has three tokens, which we will call P0, P1, and P2. Suppose the model then chooses A, followed by B, and the request stops after those two output tokens. These are teaching symbols, not real tokenizer output or a prediction from a particular model.

Prefill means processing the prompt. Decode means continuing generation using saved context. The KV cache is saved attention state for earlier positions, not a cache of finished text answers.

Model stepNew input processedSaved attention state afterwardNewly chosen output
PrefillP0, P1, P2State for P0, P1, P2A
First decode stepAState for P0, P1, P2, AB

Notice the one-step offset: choosing B does not mean the model has already processed B as an input. That happens only if generation continues.

#Give each job a name

Do not memorize every class. Start with these four jobs and follow one request through them:

Job in plain languageWhy it existsSGLang code name
Receive input and keep the response waitingThe client must not block every other requestTokenizerManager
Decide the next batch of workRequests compete for computation and memoryScheduler
Prepare tensors and run the modelThe GPU needs token positions, state locations, and model inputsTP worker and ModelRunner
Turn output tokens into a responseModel token IDs are not yet streamed textDetokenizerManager, then the frontend

Saved KV supports the middle two jobs. The scheduler decides which state may be reused and reserved; the selected attention path consumes the state during the model step.

#Why add scheduling and overlap?

Now introduce a second request. A is waiting for one next token; B has a long new prompt. Letting B occupy the GPU for too long can make A's stream pause. The scheduler limits and combines work to balance this tradeoff.

Overlap solves a different problem: while the GPU computes, the CPU may have independent preparation or result-handling work to do. That saves idle time, but only if it does not overwrite state the GPU is still reading.

Try first: after the prefill above returns A, should the next forward receive the entire prompt again, or just the newly chosen token?

Check your understanding

In the ordinary cached decode path, the new input is A. Attention reuses the saved state for P0, P1, P2. The old context still matters; it is represented by cached state rather than repeated new input tokens.

This does not mean the decode step reads only one token's worth of memory. Attention can read a large cached context.

#Now connect the picture to code

Read only this short route on the first source pass:

  1. TokenizerManager.generate_request: find the dispatch and response-wait steps. There is no model forward here.
  2. Scheduler.event_loop_normal: find receive, choose batch, run, and process result.
  3. TpModelWorker.forward_batch_generation: find the conversion to ForwardBatch and the model-runner call.

Only then open lesson 5's packed-token example or the detailed reference below.

Compare with vLLM: the model still processes a prompt and then continues generation. The main difference is the control structure: vLLM's engine core turns per-request token progress into scheduler output for its workers. See the same small story in vLLM.

#4. TokenizerManager is more than tokenization

In the inspected generate_request path:

  1. Ensure the output-handling loop is active.
  2. Normalize batch arguments, priority, and request state.
  3. Respect pause/update synchronization and validate/resolve LoRA.
  4. Tokenize/process and dispatch the request.
  5. Await response updates and yield them to the caller.
  6. On failure, distinguish states never dispatched from requests that require scheduler-side abort/cleanup.

That last distinction prevents frontend validation failures from leaking request state while avoiding silent abandonment of already-dispatched work. An async generator completing is not, by itself, proof that every GPU resource has been reclaimed.

#5. Normal loop versus overlap loop

Read the two loops in scheduler.

The normal loop is approximately:

example / trace
ingest -> get next plan -> run batch -> process result -> repeat

The overlap loop allows CPU work and device work to overlap. It keeps a result queue, can process the previous batch while the current forward is outstanding, and has explicit cases where overlap is disabled.

Important details in this checkout:

  • get_next_batch_to_run returns a plan carrying both the batch to execute and the resulting running-batch state.
  • Completed prefill work can merge into the running decode batch; partially chunked requests need separate treatment.
  • run_batch coordinates schedule/forward streams and forward-state isolation.
  • A write-after-read barrier protects shared data before result processing mutates it.
  • Some sampling depends on the previous result, such as grammar advancement, and is ordered accordingly.
Invariant

CPU preparation must not overwrite host/device metadata that an in-flight forward is still reading. "Asynchronous" is not a license to remove barriers. Measure the critical path before changing synchronization.

The specialized PD and PP loops are separate paths. Understand the baseline before following them; do not assume every feature composes with overlap.

#7. Configuration is part of reproducibility

The inspected runtime context separates:

  • raw startup configuration for provenance;
  • published resolved namespace bags;
  • runtime flags;
  • resources such as streams and buffers;
  • per-forward state;
  • configured topology and live parallel groups.

The launcher performs resolution and publishes the tokenizer role before runtime consumers read resolved bags. Other process entries establish their own process-local context. Changing a parent process's bag is not a distributed configuration broadcast.

For debugging, record effective configuration, model revision, selected backend, and rank topology. The raw command line alone may miss model- or hardware-driven resolution. A value specific to a draft runner is also not necessarily the target runner's resolved value.

#8. Where the scope expands

  • Multimodal processors add media processing and feature/position alignment.
  • Disaggregation adds transfer, readiness, and ownership state machines.
  • Speculative execution changes proposal, verification, accepted-token, and cache lifetimes.
  • LoRA adds adapter residency and execution state.
  • Distributed layers and MoE layers add collective ordering.

All of these still need explicit owners, state transitions, and cleanup. The deep dives explain the most important invariants.
